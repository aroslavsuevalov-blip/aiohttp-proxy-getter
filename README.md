# async-get-distributed

Распределённая асинхронная отправка GET-запросов на Python (`asyncio` + `aiohttp`).

## Что делает скрипт

Скрипт отправляет заданное число GET-запросов (`TOTAL_REQUESTS`) на один URL (`TARGET_URL`) с ограниченной степенью параллелизма, ротацией прокси и User-Agent, повторами при ошибках и итоговой сводкой статистики. Все запросы выполняются в одном процессе и одном event loop — «распределённость» здесь означает распределение работы между воркерами и выход наружу через список прокси, а не несколько машин.

## Как это работает

### Точка входа и event loop

`asyncio.run(main())` создаёт единственный event loop, запускает `main()` и закрывает loop. Внутри всё однопоточное и кооперативное: код выполняется до ближайшего `await`, который не готов, — дальше управление возвращается циклу, и он берёт следующую задачу. Для сетевого I/O это ровно то, что нужно: 15 задач «висят» на коннекте/DNS/TLS и не занимают CPU.

### Очередь и воркеры

`main()` заполняет `asyncio.Queue` номерами запросов и запускает ровно `MAX_WORKERS` (15) воркеров через `asyncio.create_task`. Каждый воркер в цикле берёт номер из очереди, выполняет `fetch()` и вызывает `queue.task_done()` в `finally`. Когда все задачи обработаны, `queue.join()` завершается; затем воркеры получают `None` как сигнал на выход и собираются через `asyncio.gather(..., return_exceptions=True)`.

Очередь, а не список корутин, — чтобы память не росла вместе с числом запросов: при миллионе задач здесь будет один миллион простых целых в очереди, а не миллион объектов `Task`.

Ожидание ограничено `QUEUE_JOIN_TIMEOUT`; по таймауту воркеры отменяются, чтобы зависший прогон не висел вечно.

### Два уровня ограничения параллелизма

1. Число воркеров = 15 — одновременно выполняется не больше 15 запросов, потому что воркер занят, пока не завершится `fetch()`.
2. `aiohttp.TCPConnector(limit=15, limit_per_host=15)` — верхняя граница одновременных TCP-соединений на уровне транспорта.

Первый уровень ограничивает задачи, второй — сокеты.

### Одна сессия на весь прогон

`ClientSession` владеет пулом соединений. Создавать её на каждый запрос — потеря пулинга и утечка. Параметр `proxy=` передаётся на запрос, поэтому одна сессия спокойно ходит через разные прокси; коннектор держит пул для каждой пары (прокси, схема).

`await response.read()` — не формальность: пока тело не прочитано, соединение не возвращается в пул, и коннектор его закрывает.

Таймаут задан один раз при создании сессии: `ClientTimeout(total=10, connect=5, sock_read=8)`.

### Выбор прокси: ProxyPool

Перед каждым запросом `pool.acquire(avoid=previous)` берёт прокси из «мешка» (`deque`, заполняется `random.sample` — каждый прокси ровно один раз за круг, повтор подряд невозможен). Параметр `avoid` не даёт дважды подряд взять тот же прокси, что при маленьком списке заметно разгружает очередь.

Здоровье отслеживается по счётчику неудач:

- `report_failure()` увеличивает счётчик; при `PROXY_FAILURE_LIMIT` (3) прокси уходит в карантин и перестаёт выдаваться;
- `report_success()` уменьшает счётчик на 1, а после `PROXY_SUCCESS_RESET` (2) подряд идущих успехов полностью его обнуляет;
- если в карантине оказались все прокси — здоровье сбрасывается целиком с пометкой в логе, иначе прогон умрёт насовсем.

### Заголовки

Перед каждым запросом из `USER_AGENTS` случайным образом выбирается User-Agent.

### Цикл попыток fetch()

На каждый запрос до `MAX_ATTEMPTS` (3) попыток:

1. `await cooldown.wait()` — если цель недавно отвечала 429, все воркеры ждут общий cooldown;
2. выбор прокси и User-Agent;
3. запрос в `try`;
4. при ошибке — фиксация в `stats`, откат здоровья прокси и бэкофф `backoff_delay(attempt)`: экспоненциальный `0.5 * 2^(n-1)` с капом 8 секунд и случайным джиттером, чтобы воркеры не стучались синхронно.

Классификация ответов и ошибок:

- **429** — `TargetRateLimited`: парсер `Retry-After` (поддерживает и секунды, и HTTP-date), общий cooldown `min(MAX_COOLDOWN, retry_after)`. Прокси не штрафуется: виноват лимит цели, а не канал.
- **403, 407, 502, 503, 504** — `ProxyRejected`: прокси считается виновным, +1 к неудачам.
- **сетевые ошибки** — `aiohttp.ClientError` (все варианты коннекта, TLS, разрывов), таймауты, `OSError` (закрывает `ssl.SSLError`): тоже штраф прокси.

Все эти исключения ловятся внутри `fetch()` — мёртвый прокси или таймаут не прерывают прогон, воркер просто идёт к следующей попытке. Неожиданные ошибки ловит `worker()` — они попадают в статистику и не убивают воркер. Отмена (`CancelledError` — `BaseException`) проходит насквозь штатно.

### Статистика

`Stats` считает успехи, провалы, байты, распределение статистических кодов и типы ошибок. `report()` печатает сводку: `ok`, `failed`, `total`, `bytes`, словарь статусов, ошибок и итоговые счётчики прокси.

## Возможности

- 15 воркеров + пул соединений `TCPConnector(limit=15)`
- ротация прокси и User-Agent перед каждым запросом, карантин мёртвых прокси
- очередь `asyncio.Queue` — масштабируется на миллионы запросов
- повторы с экспоненциальным бэкоффом и джиттером, обработка 429 и `Retry-After`
- глобальный cooldown при rate limit, таймаут `queue.join()` с отменой воркеров
- ошибки подключения/таймаута не прерывают прогон, итоговая сводка

```bash
pip install -r requirements.txt
python async_get.py
```

## Настройка

Константы в начале `async_get.py`:

| Константа | Назначение |
|---|---|
| `TARGET_URL` | целевой URL |
| `PROXY_LIST` | список прокси `http://ip:port` |
| `USER_AGENTS` | список User-Agent |
| `MAX_WORKERS` | число параллельных воркеров |
| `TOTAL_REQUESTS` | общее число запросов |
| `MAX_ATTEMPTS` | попыток на запрос |
| `QUEUE_JOIN_TIMEOUT` | лимит времени на весь прогон, сек |
| `PROXY_FAILURE_LIMIT` | неудач до карантина прокси |
| `PROXY_SUCCESS_RESET` | успехов подряд до сброса счётчика |
| `REQUEST_TIMEOUT` | таймауты запроса (total/connect/sock_read) |

## Легальное применение той же техники

Пул воркеров, семафор/ограничение параллелизма, пул соединений, бэкофф и обработка rate limit — это нейтральная инфраструктура для HTTP-клиента. Примеры применений в пределах правил и условий использования:

- **Нагрузка на свой сайт.** Ровно этот код (пул воркеров, ограничение параллелизма, пул соединений, бэкофф) — нормальный инструмент для проверки своего бэкенда. Цельте свой домен, это работает отлично. Начинайте с малого `TOTAL_REQUESTS`, смотрите `summary`, добавляйте нагрузку постепенно и не гоняйте нагрузочные тесты на боевом домене без согласования с хостингом.
- **TikTok Research API** — для академических исследований, доступ по заявке, официальный выгрузчик.
- **Display API / Commercial Content API** — если нужна рекламная статистика или собственный контент.
- **Свой контент** — если вы автор видео, есть официальные endpoints для статистики по своим роликам.

Для работы с официальными API укажите нужный endpoint в `TARGET_URL`, добавьте свои ключи/токены в заголовки и соблюдайте их квоты: `Retry-After` и 429 скрипт уже обрабатывает, а прокси-ротацию и смену User-Agent для официальных API с персональной авторизацией стоит отключить — они там не нужны и только мешают учёту квот.

Нельзя: целиться в чужие домены без разрешения, обходить блокировки и антибот-защиту, превращать скрипт в спам или инструмент злоупотребления. Используйте скрипт только с ресурсами, к которым у вас есть право на доступ.
